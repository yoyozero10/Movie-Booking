ID and Name:
	UC-1 Admin manages exam catalog
	Created By:
	Minh-Khoa Tu
	Date Created:
	10/10/25
	Primary Actor:
	Admin
	Secondary Actors:
	Exam Catalog Service
	Description:
	An Admin manages the exam catalog by creating, updating, publishing, or archiving exams and maintaining their metadata (category, title, description, tags, visibility, and state).
	Trigger:
	Admin selects the Exam Catalog function from the admin dashboard.
	Preconditions:
	PRE-1. Admin is authenticated into the system.
PRE-2. Admin holds a role permitted to manage exams.
	Postconditions:
	POST-1. Exam catalog entries are stored with the requested changes.
POST-2. Only exams in Published state are visible to visitors and candidates.
POST-3. Archived exams are removed from public listings, while existing attempts remain accessible.
	Normal Flow:
	1.0 Maintain exam catalog
 1. Admin opens the Exam Catalog page.
 2. System displays a list of exams with filters by category, state, and keyword search.
 3. Admin chooses Create exam.
 4. Admin enters mandatory fields: category, exam title, short description, visibility, and target level.
 5. Admin selects initial state (Draft or Published).
 6. System validates the input and ensures the exam belongs to exactly one category.
 7. System creates the exam in state Draft and shows it in the list.
 8. Admin may select an existing exam to edit metadata (description, tags, visibility).
 9. System validates edited values and saves the changes.
10. When ready, Admin chooses Publish exam.
11. System sets exam state to Published and updates public listings.
12. Admin may later choose Archive exam.
13. System sets exam state to Archived and removes it from public listings.
	Alternative Flows:
	1.1 Update existing exam metadata
1. From step 8 of normal flow, Admin changes one or more fields (e.g., description, tags).
2. System validates changes and saves them.
3. System returns to the exam list view.


1.2 Filter and search exams
1. At step 2, Admin sets filters (category, state, keyword).
2. System applies filters and refreshes the list of exams.
	Exceptions:
	1.0.E1 Invalid or incomplete exam metadata
1. System detects missing required fields or invalid values (e.g., empty title).
2. System highlights invalid fields and shows an error message.
3. Admin corrects data and resubmits; system resumes from step 6.


1.0.E2 Unauthorized catalog operation
1. System detects that the logged-in user lacks permission to create/publish/archive exams.
2. System rejects the operation and shows an authorization error message.
	Priority:
	High
	Frequency of Use:
	Used daily by Admins; peak usage occurs when preparing for new exam sessions or academic terms.
	Business Rules:
	BR-1, BR-2, BR-3, BR-21
	Other Information:
	1. Admin shall be able to preview how an exam will appear to candidates before publishing it.
2. Admin shall be able to filter exams by category, state, and keyword.
	Assumptions:
	Exam categories are managed elsewhere and change infrequently.

	ID and Name:
	UC-2 Admin edits exam structure
	Created By:
	Langfens English Team
	Date Created:
	10/12/2025
	Primary Actor:
	Admin
	Secondary Actors:
	Exam Catalog Service, Attempt Service
	Description:
	An Admin defines or updates the internal structure of an exam: sections, question groups, questions, time limits, and scoring weights.
	Trigger:
	Admin chooses Edit structure for a specific exam from the exam catalog.
	Preconditions:
	PRE-1. Admin is authenticated.
PRE-2. Target exam exists in the catalog.
PRE-3. Exam is in Draft state, or Published with no completed attempts for the current version.
	Postconditions:
	POST-1. Exam structure is stored with defined sections, questions, scoring rules, and time limits.
POST-2. If the exam already had completed attempts, a new exam version is created and updated instead of the original exam.
POST-3. Delivery snapshots for new attempts use the updated structure.
	Normal Flow:
	1.0 Configure exam structure
1. Admin opens the exam details and selects Edit structure.
2. System shows the current section/question layout or an empty structure for a new exam.
3. Admin adds or edits sections (e.g., Listening, Reading, Writing, Speaking) and sets their order and weights.
4. For each section, Admin adds questions, defines question type, content, answer options, and scoring rule.
5. Admin sets global exam settings (overall time limit, maximum score, shuffle settings).
6. System validates structure consistency (e.g., weights sum, mandatory content present).
7. Admin saves the structure.
8. System stores the structure and marks the exam version as structurally complete.
	Alternative Flows:
	1.1 Copy structure from existing exam
1. At step 3, Admin chooses Copy from existing exam.
2. System displays a list of compatible source exams.
3. Admin selects a source exam.
4. System copies its structure into the current exam and returns to step 3 for further editing.


1.2 Create new exam version due to existing attempts
1. When Admin saves (step 7), System detects that the current exam version already has completed attempts.
2. System prompts Admin to confirm creating a new version.
3. If Admin confirms, System creates a new Draft version and applies the structure changes there.
	Exceptions:
	1.0.E1 Invalid scoring configuration
1. System finds inconsistent scoring (e.g., no questions, negative weights).
2. System shows detailed errors and cancels the save operation.
3. Admin fixes configuration and retries from step 6.


1.0.E2 Version locked for editing
1. System detects that the exam version is locked by another Admin or by a publishing workflow.
2. System informs Admin and prevents changes.
	Priority:
	High
	Frequency of Use:
	Used whenever new exams are created or existing exams are updated, especially before major testing campaigns.
	Business Rules:
	BR-2, BR-3, BR-4, BR-5, BR-23, BR-25 
	Other Information:
	1. Admin should be able to preview a simulated attempt based on the current structure.
2. Changes to writing and speaking tasks do not affect existing attempts; they apply only to future attempts.
	Assumptions:
	Question content may come from an external question bank but is referenced within this structure.

	Attempt Service, Reporting Service
	Description:
	Admin views and analyzes ongoing and completed exam attempts, including status, timing, and scores.
	Trigger:
	Admin selects Attempts & Results from the admin dashboard.
	Preconditions:
	PRE-1. Admin is authenticated.
PRE-2. Exams and attempts already exist in the system.
	Postconditions:
	POST-1. No attempt data is changed unless Admin explicitly performs allowed maintenance actions.
POST-2. Any administrative changes (e.g., forced submit) are logged for audit.
	Normal Flow:
	1.0 View attempts
1. Admin opens the Attempts & Results page.
2. System shows filters (exam, candidate, date range, status).
3. Admin sets filters and clicks Search.
4. System lists matching attempts with key metrics (status, start time, finish time, score).
5. Admin selects an attempt to inspect.
6. System displays attempt details based on the delivery snapshot (per-section scores, responses, timing).
7. Admin may assign or update graders for writing/speaking tasks.
8. System stores grader assignments.
9. Admin may export results for a selected exam or date range.
10. System generates an export file and provides it for download.
	Alternative Flows:
	1.1 Force submit stuck attempt
1. Admin identifies an attempt in status In progress that has exceeded maximum allowed time.
2. Admin chooses Force submit.
3. System finalizes the attempt, computes scores if possible, sets status (e.g., Completed – Forced), and logs the action.
	Exceptions:
	1.0.E1 Attempt data unavailable
1. System cannot load attempt details because the delivery snapshot is missing or corrupted.
2. System informs Admin and logs an incident.
3. Admin flags the attempt for manual resolution.
	Priority:
	Medium
	Frequency of Use:
	Used regularly after exam sessions and during grading periods.
	Business Rules:
	BR-5, BR-6, BR-7, BR-8, BR-11, BR-23, BR-24, BR-25 
	Other Information:
	Only authorized staff may see personally identifiable information in attempt views.
	Assumptions:
	Standard export formats (CSV/Excel) are configured in advance.

	Created By:
	Langfens English Team
	Date Created:
	10/12/2025
	Primary Actor:
	Admin or Content Creator
	Secondary Actors:
	Vocabulary Service
	Description:
	Admin or a designated content creator manages vocabulary decks and cards used for spaced-repetition review.
	Trigger:
	Actor selects the Vocabulary module from the admin dashboard.
	Preconditions:
	PRE-1. Actor is authenticated.
PRE-2. Actor has permission to manage vocabulary content.
	Postconditions:
	POST-1. Vocabulary decks and cards are stored and associated with each other.
POST-2. Only Published decks and cards are visible to learners and the public.
POST-3. Archived decks are hidden from new subscriptions, but existing review history remains accessible.
	Normal Flow:
	1.0 Maintain vocabulary decks
1. Actor opens the Vocabulary module.
2. System displays a list of existing decks with filters (topic, level, state, keyword).
3. Actor chooses Create deck.
4. Actor enters deck attributes: title, description, tags, target level, visibility, initial state (Draft / Published).
5. System validates input and creates the deck in Draft state.
6. Actor opens the deck and adds vocabulary cards.
7. For each card, Actor defines term, pronunciation, meaning, example sentence, and optional notes.
8. System validates card data and saves it, associating each card with the deck.
9. When the deck is ready, Actor chooses Publish deck.
10. System sets deck and its cards to Published and includes the deck in public vocabulary listings.
	Alternative Flows:
	1.1 Edit existing deck
1. At step 2, Actor selects an existing deck.
2. Actor updates title, description, tags, or level.
3. System validates and saves changes.

1.2 Archive deck
1. Actor selects a Published deck.
2. Actor chooses Archive deck.
3. System confirms that archived decks will not accept new subscribers.
4. Actor confirms; System sets deck state to Archived.
	Exceptions:
	1.0.E1 Unauthorized modification
1. System detects that the user does not have permission to create or edit decks.
2. System rejects the operation and displays an authorization error.

1.0.E2 Invalid card data
1. System detects missing required card fields (e.g., empty term or meaning).
2. System highlights invalid fields and prevents saving until corrected.
	Priority:
	Medium
	Frequency of Use:
	Used whenever vocabulary content is curated; frequency depends on content-creation schedule.
	Business Rules:
	BR-12, BR-13, BR-14, BR-20, BR-21
	Other Information:
	Deck statistics (number of subscribers, review accuracy) may be displayed to help prioritize maintenance.
	Assumptions:
	Import/export of deck content from spreadsheets is handled by a separate feature.

	Description:
	Admin configures speaking tasks within exams, including prompts, audio materials, timings, and evaluation criteria.
	Trigger:
	Admin opens the Speaking section in the structure of a specific exam.
	Preconditions:
	PRE-1. Admin is authenticated.
PRE-2. Target exam exists and is in Draft state, or Published with no completed attempts for the current version.
PRE-3. Admin has permission to edit exam structures.
	Postconditions:
	POST-1. Speaking tasks are stored as part of the exam structure.
POST-2. New attempts use the updated speaking configuration.
POST-3. Existing attempts for previous versions remain unchanged.
	Normal Flow:
	1.0 Configure speaking tasks
1. Admin opens the exam and navigates to the Speaking section.
2. System shows existing speaking tasks or an empty list.
3. Admin creates or edits a speaking task, specifying prompt, optional image/audio, preparation time, and response time.
4. Admin associates scoring rubric criteria (e.g., Fluency, Lexical resource, Grammar, Pronunciation) and band descriptors with the task.
5. Admin reorders tasks if needed.
6. Admin saves the speaking section.
7. System validates that at least one task exists and that timings and rubrics are consistent.
8. System stores speaking tasks as part of the exam structure.
	Alternative Flows:
	1.1 Attach sample question audio
1. At step 3, Admin uploads an audio file for a task.
2. System stores the file in media storage and links it to the task.
3. System updates the preview so Admin can play the audio.
	Exceptions:
	1.0.E1 Exam version locked by existing attempts
1. Upon saving at step 7, System detects completed attempts for this exam version.
2. System prevents direct modification and offers to create a new exam version.
3. If Admin confirms, System creates a new Draft version and applies changes there.

1.0.E2 Invalid speaking configuration
1. System detects invalid timing (e.g., response time = 0) or missing rubric information.
2. System highlights errors and prevents saving until corrected.
	Priority:
	Medium
	Frequency of Use:
	Used when speaking content is created or updated for new exam versions.
	Business Rules:
	BR-4, BR-5, BR-8, BR-23, BR-24, BR-25
	Other Information:
	Speaking responses may be recorded and stored for later grading by human assessors or external tools.
	Assumptions:

	Description:
	A user logs into the system using either email and password or a linked Google account.
	Trigger:
	User clicks Log in on the website.
	Preconditions:
	PRE-1. User already has an account on the platform or a Google account that can be linked.
PRE-2. Account is not locked or disabled.
	Postconditions:
	POST-1. A new authenticated session (or token) is created for the user.
POST-2. Session timeout is scheduled based on configuration and “Remember me” choice.
POST-3. Last login timestamp is updated.
	Normal Flow:
	1.0 Log in with email and password
1. User clicks Log in.
2. System displays a login form with options Email & Password and Continue with Google.
3. User selects Email & Password, enters credentials, and submits.
4. System validates credentials against stored account data.
5. System checks that the email has been verified.
6. If valid, System creates a session for the user and redirects to the learner dashboard.
	Alternative Flows:
	1.1 Log in with Google
1. At step 3, user chooses Continue with Google.
2. System redirects user to Google OAuth consent screen.
3. User reviews and grants permission.
4. Google redirects back with authorization code / token.
5. System validates the token and retrieves user identity information.
6. If a matching local account exists, System logs the user in and creates a session.
7. If no local account exists, System may create a linked account according to business rules and log the user in.

1.2 Remember me
1. At step 3, user selects Remember me.
2. System sets a longer-lived refresh token or cookie within security policy constraints.
	Exceptions:
	1.0.E1 Invalid credentials
1. At step 4, System detects incorrect email or password.
2. System shows an error message and allows the user to retry.

1.0.E2 Account not verified
1. At step 5, System detects the account has not completed email verification.
2. System blocks login, informs the user, and offers a link to resend verification OTP.

1.1.E1 Google authentication failed
1. Google rejects the authentication or returns an error.
2. System informs the user that Google login failed and returns to the login page.
	Priority:
	High
	Frequency of Use:
	Used daily by active learners and candidates.
	Business Rules:
	BR-15, BR-18, BR-19, BR-20, BR-21, BR-22
	Other Information:
	Failed login attempts may be logged for security monitoring and account lockout policies.
	Assumptions:
	Google OAuth configuration is correctly set up and network connectivity is available.

	Langfens English Team

	10/12/2025
	Primary Actor:
	User (Forgotten Password)
	Secondary Actors:
	Email Service, OTP Service
	Description:
	A user who forgot the password requests a reset link or OTP via email, verifies it, and sets a new password.
	Trigger:
	User clicks Forgot password on the login page.
	Preconditions:
	PRE-1. User has a registered email address in the system.
	Postconditions:
	POST-1. User account password is updated to the new value.
POST-2. Any active sessions created with the old password may be revoked according to security policy.
	Normal Flow:
	1.0 Request password reset
1. User clicks Forgot password.
2. System displays a form to enter the registered email address.
3. User enters email and submits.
4. System checks that the email exists and account is not blocked.
5. System generates a reset OTP or token and sends an email with instructions.
6. System shows a screen asking the user to enter the OTP and the new password.
7. User enters received OTP and a new password, then submits.
8. System validates the OTP (correct, not expired, not previously used).
9. System validates the new password against password policy.
10. System updates the stored password hash and confirms success to the user.
	Alternative Flows:
	1.1 Resend reset OTP
1. At step 6, if user does not receive the email, user chooses Resend OTP.
2. System checks rate limits and, if allowed, issues a new OTP and email, invalidating previous ones.
3. Flow returns to step 7.
	Exceptions:
	1.0.E1 Email not found
1. At step 4, System cannot find an account with the given email.
2. System shows an error message but does not reveal whether the email exists, depending on security policy.

1.0.E2 OTP invalid or expired
1. At step 8, System detects an invalid or expired OTP.
2. System informs the user and allows re-entry or to request a new OTP (Alt Flow 1.1).
	Priority:
	High
	Frequency of Use:
	Occurs when users forget passwords; relatively infrequent compared to login.
	Business Rules:
	BR-15, BR-16, BR-17, BR-18, BR-19, BR-22

	ID and Name:
	UC-12 System sends and verifies OTP emails
	Created By:
	Langfens English Team
	Date Created:
	10/12/2025
	Primary Actor:
	System (OTP Service)
	Secondary Actors:
	Email Service
	Description:
	Internal service use case in which the system generates, sends, stores, and verifies time-limited OTP codes for registration and password reset.
	Trigger:
	Another use case (e.g., UC-8 or UC-11) requests OTP generation or verification.
	Preconditions:
	PRE-1. Email infrastructure is configured.
PRE-2. Caller provides a valid email address and OTP context (registration / reset).
	Postconditions:
	POST-1. New OTP record is stored with value, expiration time, and usage status.
POST-2. OTP email is queued for sending via Email Service.
POST-3. On verification, OTP is marked as used and cannot be reused.
	Normal Flow:
	1.0 Generate and send OTP
1. Calling use case requests an OTP for a given email and purpose.
2. System checks rate-limit rules for that email and purpose.
3. System generates a random OTP value and expiration timestamp.
4. System stores OTP record associated with the email and purpose.
5. System sends an email containing the OTP and explanatory text.

1.1 Verify OTP
6. When user submits an OTP, calling use case sends email, OTP value, and purpose to the OTP service.
7. System retrieves latest unused OTP record matching the email and purpose.
8. System checks value match and expiration.
9. If valid, System marks OTP as used and returns Verified to the caller.
	Alternative Flows:
	1.2 Invalidate previous OTPs
1. When a new OTP is generated at step 3, System may mark all previous unused OTPs for the same email and purpose as Invalid.
2. Only the newest OTP will be accepted.
	Exceptions:
	1.0.E1 Rate-limit exceeded
1. At step 2, System detects too many OTP requests for the email in a short period.
2. System denies generation and returns an error to the calling use case.

1.1.E1 OTP not found or invalid
1. At step 7–8, System finds no matching valid OTP.
2. System returns Invalid/Expired status to the caller.
	Priority:
	High (supporting critical flows UC-8 and UC-11)
	Frequency of Use:
	Whenever users register, verify email, or reset password.
	Business Rules:
	BR-16, BR-17, BR-18, BR-19
	Other Information:
	OTP length, validity duration, and rate limits are configurable system parameters.
	Assumptions:
	Email service is monitored to ensure acceptable delivery rate and latency.

	Created By:
	Langfens English Team
	Date Created:
	10/12/2025
	Primary Actor:
	Learner (authenticated user)
	Secondary Actors:
	Course Service, Progress Tracking Service, Payment Service (if needed)
	Description:
	A learner enrolls in a Published course and the system tracks completion progress of lessons.
	Trigger:
	Learner clicks Enroll on a course detail page.
	Preconditions:
	PRE-1. Learner is logged in.
PRE-2. Target course is Published and open for enrollment.
PRE-3. Any payment or access conditions (if applicable) are satisfied.
	Postconditions:
	POST-1. Enrollment record is created linking learner and course.
POST-2. Initial progress is set (e.g., 0% complete).
POST-3. As lessons are completed, progress metrics are updated.
	Normal Flow:
	1.0 Enroll in course
1. Learner opens a Published course detail page.
2. System indicates whether the learner is already enrolled.
3. If not enrolled, learner clicks Enroll.
4. If the course requires payment, System redirects to payment flow (outside this UC) and waits for success.
5. System creates an enrollment record with initial status (e.g., Active) and start date.
6. System redirects learner to the course lesson list.
	Alternative Flows:
	1.1 Resume course and update progress
1. From dashboard, learner opens an already enrolled course.
2. System shows lesson list indicating completed/in-progress/not-started lessons.
3. Learner opens a lesson and completes learning activities (e.g., watching video, answering quiz).
4. On completion criteria, System marks the lesson as completed and recalculates course progress percentage.
5. If all mandatory lessons are completed, System marks course status as Completed for the learner.
	Exceptions:
	1.0.E1 Enrollment not allowed
1. At step 3, System detects that course is Archived or enrollment period ended.
2. System prevents enrollment and shows an explanatory message.
	Priority:
	High
	Frequency of Use:
	Frequently by active learners.
	Business Rules:
	BR-9, BR-10, BR-11, BR-20, BR-21
	Other Information:
	Course progress may influence recommendation and certification features.
	Assumptions:
	Payment handling (if any) is implemented in a separate use case.

	ID and Name:
	UC-17 Learner subscribes and reviews flashcards
	Created By:
	Langfens English Team
	Date Created:
	10/12/2025
	Primary Actor:
	Learner (authenticated user)
	Secondary Actors:
	Vocabulary Service, Spaced Repetition Engine
	Description:
	A learner subscribes to a deck and regularly reviews vocabulary cards according to a spaced-repetition schedule.
	Trigger:
	Learner clicks Subscribe on a deck detail page or Review now on the vocabulary dashboard.
	Preconditions:
	PRE-1. Learner is logged in.
PRE-2. Target deck is Published and not Archived.
PRE-3. Learner has not exceeded any subscription limit (if defined).
	Postconditions:
	POST-1. Subscription record is created linking learner and deck.
POST-2. Review sessions generate scheduling data for each card.
POST-3. Performance statistics (correct / incorrect) are stored and used to adjust future intervals.
	Normal Flow:
	1.0 Subscribe to deck
1. Learner opens a Published deck detail page.
2. System indicates whether the learner has already subscribed.
3. If not, learner clicks Subscribe.
4. System creates a subscription record with initial set of active cards and next-review dates.
5. System redirects learner to the Review screen.

1.1 Review flashcards
6. On the Review screen, System selects due cards according to spaced-repetition rules.
7. System shows the front side of the first card (term or definition).
8. Learner reveals the back side and marks the answer as Easy, Good, or Hard (or similar scale).
9. System records the result and adjusts the next-review date for that card.
10. Steps 7–9 repeat for remaining due cards.
11. At the end of the session, System shows a summary of cards reviewed and performance.
	Alternative Flows:
	1.2 Suspend subscription
1. From deck subscription settings, learner chooses Pause deck.
2. System marks the subscription as paused and temporarily stops scheduling new reviews.
	Exceptions:
	1.0.E1 Deck archived after subscription
1. When learner starts a review at step 6, System detects that the deck has been Archived.
2. System may allow reviewing existing cards but prevents new learners from subscribing; learner is informed that the deck is no longer maintained.
	Priority:
	High
	Frequency of Use:
	Frequent for active learners focusing on vocabulary.
	Business Rules:
	BR-12, BR-13, BR-14, BR-20, BR-21
	Other Information:
	Deck performance data can be aggregated for Admin dashboards (e.g., difficult cards).
	Assumptions:
	Spaced-repetition algorithm parameters are configurable (intervals, ease factors).

	ID and Name:
	UC-18 Candidate takes an exam attempt
	Created By:
	Langfens English Team
	Date Created:
	10/12/2025
	Primary Actor:
	Candidate (authenticated learner)
	Secondary Actors:
	Attempt Service, Exam Catalog Service, Delivery Engine, Timer Service
	Description:
	A candidate starts an exam, completes all required sections within time limits, submits the attempt, and the system stores responses and calculates scores.
	Trigger:
	Candidate clicks Start exam on a Published exam detail page.
	Preconditions:
	PRE-1. Candidate is logged in.
PRE-2. Exam is in Published state and available for the candidate.
PRE-3. Candidate meets any eligibility conditions (e.g., payment, attempts remaining).
	Postconditions:
	POST-1. An exam attempt record is stored with responses and timing data.
POST-2. Scores are calculated for auto-scorable parts (e.g., Listening, Reading).
POST-3. Attempt status is set to Completed (or equivalent) and visible in candidate’s history.
POST-4. For writing and speaking tasks, responses are stored for later grading.
	Normal Flow:
	1.0 Take an exam
1. Candidate opens a Published exam detail page.
2. System checks if the candidate has any in-progress attempt for this exam.
3. If not, candidate clicks Start exam.
4. System creates a new attempt record and generates a delivery snapshot of the exam structure and content for this attempt.
5. System displays exam instructions and time limit; candidate confirms to begin.
6. System starts the exam timer and shows the first section.
7. Candidate answers questions section by section, navigating using Next / Back within allowed rules.
8. System autosaves responses and remaining time periodically.
9. When candidate completes all sections, candidate clicks Submit exam.
10. System asks for confirmation and then finalizes the attempt, stopping the timer.
11. System calculates scores for objective questions and derives section and overall scores where applicable.
12. System stores all responses, scores, and timing information, and updates attempt status to Completed.
	Alternative Flows:
	1.1 Auto-submit when time expires
1. During step 7–8, if remaining time reaches zero, Timer Service automatically triggers submission.
2. System finalizes the attempt using current responses, marks it as Completed – Time expired, and performs scoring as in steps 11–12.

1.2 Resume in-progress attempt
1. At step 2, System detects an existing in-progress attempt within allowed resumption window.
2. Candidate chooses Resume attempt instead of starting a new one.
3. System loads delivery snapshot and current responses, restores remaining time, and returns to step 6.
	Exceptions:
	1.0.E1 Exam not available
1. At step 3, System detects that exam has been Archived or candidate does not have access (quota exceeded, payment missing).
2. System prevents starting the exam and shows an explanatory message.

1.0.E2 Connectivity or browser crash
1. Candidate loses connection or closes the browser during step 7–8.
2. System continues to track time server-side.
3. When candidate logs back in within allowed resumption window, System offers to resume attempt (Alt Flow 1.2) or, if time expired, shows that the attempt has been auto-submitted.
	Priority:
	Critical
	Frequency of Use:
	Very frequent during mock-exam campaigns.
	Business Rules:
	BR-2, BR-4, BR-5, BR-6, BR-7, BR-8, BR-20, BR-23, BR-25
	Other Information:
	For high-stakes exams, additional proctoring rules (camera, identity check) may apply and are handled by related use cases or external tools.
	Assumptions:
	Candidate’s device and browser meet minimum technical requirements for the exam.

	ID and Name:
	UC-20 Internal services fetch delivery snapshot
	Created By:
	Langfens English Team
	Date Created:
	10/12/2025
	Primary Actor:
	Attempt Service (internal)
	Secondary Actors:
	Exam Catalog Service, Storage Service
	Description:
	Internal services retrieve the immutable delivery snapshot associated with an exam attempt for scoring, review, or monitoring, instead of reading live exam definitions.
	Trigger:
	Another process (e.g., scoring engine, admin monitoring UI, candidate review UI) requests attempt content.
	Preconditions:
	PRE-1. A delivery snapshot was created for the attempt in UC-18.
PRE-2. Attempt identifier is valid.
	Postconditions:
	POST-1. Snapshot data is returned to the caller for read-only purposes.
POST-2. Live exam definitions remain unaffected by snapshot retrieval.
	Normal Flow:
	1.0 Fetch delivery snapshot
1. Caller sends an attempt ID to the Attempt Service requesting details.
2. Attempt Service loads basic attempt data (status, candidate, timestamps).
3. Attempt Service locates the associated delivery snapshot stored when the attempt was started.
4. Attempt Service returns snapshot content (sections, questions, choices, scoring rules) together with candidate responses.
5. Caller uses the snapshot for scoring, display, or reporting.
	Alternative Flows:
	1.1 Cache snapshot
1. If the same attempt is requested repeatedly, Attempt Service may cache the snapshot in memory for performance.
2. Subsequent requests reuse the cached version until eviction.
	Exceptions:
	1.0.E1 Snapshot not found
1. At step 3, Attempt Service cannot find a snapshot record for the attempt.
2. Service logs an error and returns an error status to caller.
3. Caller may show a message to Admin and mark the attempt for manual investigation.
	Priority:
	High (foundation for reliable scoring and review)
	Frequency of Use:
	Used whenever attempts are viewed or scored.
	Business Rules:
	BR-5, BR-25
	Other Information:
	Snapshot data is read-only; any fixes to exam content are done via new exam versions, not by editing snapshots.
	Assumptions:
	Snapshot storage is durable and backed up regularly.
