1. Introduction
1.1 Purpose 
This Software Requirements Specification (SRS) describes the functional and nonfunctional requirements for Release 1.0 of the Movie-Booking Website. This system is a full-stack web application that allows users to browse movies, check showtimes, and book tickets online. This document is intended to be used by the project's developers, testers, and stakeholders to guide design, implementation, and verification.
1.2 Document Conventions
The functional requirements in Section 3 are organized by User Class, with specific Use Cases (UC) detailed for each class. This approach aligns the system's features with the perspectives of its end-users.
1.3 Project Scope and Product Features
Vision: To provide a seamless, secure, and modern online platform for moviegoers to discover films and book their tickets, replacing the inconvenience of in-person or phone-based booking.

Scope: The product is a decoupled, full-stack application.
* Frontend: A client-side application built with React + Vite, responsible for all user-facing interactions.
* Backend: A secure RESTful API built with Express.js + MongoDB, responsible for business logic, data management, and user authentication.
* Features: The system will manage movie listings, theater showtimes, user accounts, and the complete booking process from seat selection to confirmation.

2. Overall Description
2.1 User Classes and Their Use Cases
The system has three (3) primary user classes:
2.1.1 Visitor (Unauthenticated) A user who has not logged into the system.
Use Cases:
* UC-V-1: Explore and Search Movies
* UC-V-2: View Showings
* UC-V-3: Register for an Account
* UC-V-4: Log In
2.1.2 Registered User (Authenticated) A user who has successfully registered and logged in.
Use Cases:
* (All Visitor use cases)
* UC-U-1: Manage User Profile
* UC-U-2: Book Ticket
* UC-U-3: View Booking History
2.1.3 Administrator A privileged user (role implied by backend CRUD features) responsible for managing system content.
Use Cases:
* UC-A-1: Manage Movies (CRUD)
* UC-A-2: Manage Showings (CRUD)
* UC-A-3: Manage Bookings (CRUD)
* UC-A-4: Manage Users (Implied)
2.2 Operating Environment
*  OE-1: The frontend application shall be deployed and hosted on Netlify.
*  OE-2: The backend API shall be deployed and hosted on Render.
*  OE-3: The database shall be a cloud-hosted MongoDB Atlas cluster.
*  OE-4: The system shall be accessible via modern web browsers (e.g., Google Chrome, Mozilla Firefox, Apple Safari, Microsoft Edge) on both desktop and mobile platforms.
2.3 Design and Implementation Constraints
The system design and implementation shall adhere to the following constraints:
* CO-1 (Frontend Stack): The client-side application shall be built using React 19 combined with TypeScript to ensure type safety. The build process and development server shall utilize Vite for performance optimization.
* CO-2 (UI/UX Design): The user interface shall be styled using Tailwind CSS following a "Glassmorphism" design system. Icons shall be implemented using Lucide React, and toast notifications shall be handled by Sonner.
* CO-3 (Language Support): The system must support internationalization (i18n), allowing users to switch between English (en) and Vietnamese (vi).
* CO-4 (Backend Stack): The server-side API shall be built on the Node.js runtime using the Express 5.0 framework.
* CO-5 (Database): Data persistence shall be managed by MongoDB (NoSQL) via the Mongoose ODM library.
* CO-6 (Authentication): User authentication shall use JSON Web Tokens (JWT). Passwords must be hashed using bcryptjs before storage.
* CO-7 (Security Standards): The backend must implement Helmet for secure HTTP headers and Express Rate Limit to prevent brute-force attacks.
* CO-8 (Payment Integration): The system shall integrate with the PayOS gateway to process secure online transactions.
* CO-9 (Quality Assurance): The project must include Jest for Unit Testing and Playwright for End-to-End (E2E) Testing.

4. Data Requirements
4.1 Logical Data Model

Figure 1. Partial data model for release 1.0 of the Movie-Booking Website.
The system's data persistence is managed by MongoDB and defined by Mongoose schemas (as implied by server/models/). The core entities are:
* User: Stores user account information, including hashed credentials and profile details.
* Movie: Stores all information related to a single film.
* Theater: (Implied) Stores information about a cinema location, including its screens and seating layouts.
* Showing: A relational entity that links one Movie to one Theater (screen) at a specific showTime.
* Booking: Stores a record of a completed transaction, linking a User, a Showing, and the specific seats they reserved.

4.3 Data Integrity, Retention and Disposal

* DI-1 (Transaction Logs): Booking and Payment logs must be retained for at least 24 months for auditing and dispute resolution purposes.
* DI-2 (Pending Bookings): Seats held in a "Pending" booking state must be automatically released if payment is not completed within 15 minutes.
* DI-3 (Account Deletion): Upon user request for account deletion, Personal Identifiable Information (PII) must be anonymized, but transaction history must be preserved for revenue accuracy.
5. External Interface Requirements
5.1  User Interfaces
*  UI-1: The UI shall be responsive and render correctly on all major device types (desktop, tablet, mobile).
*  UI-2: The UI shall adhere to the Tailwind CSS utility-first design framework.
*  UI-3: The UI shall use icons from the Lucide React library for consistent visual language.
*  UI-4: The application shall function as a Single Page Application (SPA), with navigation handled by React Router.
5.2  Software Interfaces
*  SI-1 (API): The frontend (Netlify) shall communicate with the backend (Render) via a RESTful API over HTTP, using Axios.
*  SI-2 (Database): The backend (Express.js) shall interface with the MongoDB Atlas cluster via the Mongoose ODM.
*  SI-3 (Environment Config): The frontend shall fetch the backend API location from a VITE_API_BASE_URL environment variable.
*  SI-4 (Data Seeding): The project shall provide an npm run seed script to populate the database with sample data.
5.3 Hardware Interfaces
No hardware interfaces have been identified.
5.4 Communications Interfaces
*  CI-1 (Encryption): All communication between the client and servers shall be encrypted using HTTPS. (Handled by Netlify and Render).
*  CI-2 (CORS): The backend shall implement a CORS policy to only accept requests from the deployed frontend domain.
6. Quality Attributes
6.1 Performance Requirements
*  PER-1 (Build/Dev): The frontend development server and production build process shall be optimized by Vite for fast startup and optimized bundles.
*  PER-2 (Rate Limiting): The backend API shall be protected by express-rate-limit to prevent brute-force attacks and simple DoS attacks, ensuring service availability.
6.2 Security Requirements
*  SEC-1 (Token Management): Authentication shall use JWT with a defined expiration (e.g., 7 days). Tokens shall be stored securely in localStorage on the client side.
*  SEC-2 (Secure Headers): The backend shall utilize the Helmet middleware to enforce secure HTTP headers (XSS Filter, No-Sniff, HSTS).
*  SEC-3 (Rate Limiting): The API shall implement Express Rate Limit to restrict traffic to 1000 requests per 15 minutes per IP address to mitigate DDoS attacks.
*  SEC-4 (Input Sanitization): All incoming API requests must be validated and sanitized to prevent NoSQL Injection attacks.
6.3 Usability Requirements
*  USE-1 (Responsiveness): The application shall be fully functional and easy to navigate on mobile devices (see UI-1).
*  USE-2 (Clarity): The booking flow-from movie selection to seat selection to confirmation-shall be intuitive and clearly guide the user.
6.4 Maintainability Requirements
*  MAIN-1 (Modularity): The project shall be organized with a clear separation of concerns:
* src/: All frontend React code.
* server/: All backend Express.js code.
*  MAIN-2 (Backend Structure): The server/ directory shall be further modularized into controllers, middleware, models, and routes to isolate logic.
*  MAIN-3 (Config): All environment-specific variables (database strings, API keys, JWT secrets) shall be stored in .env files and not hard-coded. An .env.example file shall be provided.
*  MAIN-4 (Code Quality): The project shall include an npm run lint script to enforce code style and identify potential errors.
6.5 Testing Requirements
*  TEST-1 (Unit Testing): Critical utility functions (currency formatting, validation logic) shall be tested using Jest.
*  TEST-2 (E2E Testing): Core user flows (Login, Booking, Admin CRUD) shall be verified using automated Playwright tests.
6.6 Safety Requirements
* SAF-1 (Age Restriction): The system shall display age rating labels (e.g., C13, C18) clearly on movie details and booking screens.
* SAF-2 (Payment Safety): The system shall strictly not store sensitive credit card information (PAN, CVV) in the database. All processing is delegated to PayOS.
6.7 Availability Requirements
* AVL-1 (Uptime): The system shall aim for 99% uptime during peak operational hours (18:00 - 23:00 on weekends).
* AVL-2 (Maintenance): Scheduled maintenance should be performed during off-peak hours (02:00 - 05:00) with prior user notification.
6.8 Robustness Requirements
* ROB-1 (Payment Recovery): If a user's network disconnects during payment, the system shall provide a mechanism to "Check Transaction Status" from PayOS to re-sync the booking status (Confirmed/Failed) without double-charging.
* ROB-2 (Concurrency Handling): The system must handle race conditions where two users select the same seat simultaneously; only the first request to reach the server shall lock the seat.
